# ADR-003: Chọn AWS EC2, Docker Hub và Vercel cho triển khai hệ thống

**Ngày:** 2026-09-27  
**Trạng thái:** Accepted  
**Liên quan:** ADR-002 — Lựa chọn kiến trúc hệ thống cốt lõi

## Bối cảnh

Hệ thống cần một quy trình triển khai tách biệt giữa backend và frontend, phù
hợp với giai đoạn MVP nhưng vẫn có khả năng rollback và kiểm tra health sau mỗi
lần release. Backend gồm FastAPI và PostgreSQL/pgvector, hiện được đóng gói
bằng Docker Compose. Frontend là ứng dụng React/Vite cần được phân phối qua một
nền tảng hosting có CI/CD đơn giản.

Các yêu cầu chính:

- Hạ tầng backend phải chạy trên AWS để có một môi trường triển khai ổn định,
  kiểm soát được network và quyền truy cập.
- Backend phải được build thành Docker image có tag bất biến theo commit.
- EC2 không build source tại máy chủ; máy chủ chỉ pull image đã được CI kiểm thử
  từ Docker Hub Registry.
- Frontend cần deploy độc lập, có preview theo branch/PR và rollback thuận tiện.
- Quy trình release phải có health check, giữ release cũ và hỗ trợ rollback khi
  container mới không healthy.

## Yếu tố quyết định

- Đơn giản và phù hợp nguồn lực MVP.
- Tách build/verify khỏi máy chủ production.
- Có thể truy vết image theo commit SHA.
- Giảm downtime và có rollback rõ ràng.
- Quản lý secret ngoài source code.
- Không khóa backend vào một cơ chế build riêng của cloud provider.

## Các lựa chọn

### Lựa chọn 1: AWS EC2 + Docker Compose + Docker Hub + Vercel — chọn cho `develop`

- **Ưu điểm:** EC2 linh hoạt, chạy được Docker Compose hiện có; Docker Hub
  phù hợp với workflow build/push hiện tại; Vercel tối ưu cho frontend React;
  backend và frontend có lifecycle độc lập.
- **Nhược điểm:** Đội ngũ phải quản lý OS, Docker, PostgreSQL backup và security
  patch trên EC2; Docker Hub là thêm một dependency bên ngoài AWS.

### Lựa chọn 2: AWS ECS/Fargate + Docker Hub + Vercel — chọn cho `main`

- **Ưu điểm:** Managed orchestration tốt hơn, tích hợp IAM/ECR và autoscaling.
- **Nhược điểm:** Cấu hình và chi phí vận hành cao hơn MVP; cần quản lý task
  definition/service/networking của ECS.

### Lựa chọn 3: Một nền tảng PaaS cho cả frontend và backend

- **Ưu điểm:** Thiết lập ban đầu nhanh, ít phải quản lý máy chủ.
- **Nhược điểm:** Khó giữ mô hình EC2 + PostgreSQL Compose hiện có; ít kiểm soát
  hơn về network và quy trình pull image; frontend không tận dụng tốt preview
  và edge delivery chuyên biệt của Vercel.

## Quyết định

Chọn kiến trúc triển khai sau:

1. **AWS** là cloud provider cho hạ tầng backend và môi trường deploy.
2. **EC2** là compute host cho backend development chạy Docker Compose.
3. **ECS Fargate** là compute target cho backend production trên `main`.
4. **Docker** là đơn vị đóng gói và runtime của backend. Docker image được build
   trong GitHub Actions, không build trực tiếp trên EC2 hoặc ECS.
5. **Docker Hub Registry** là nơi lưu trữ image backend. CI push hai tag:
   - immutable tag theo `${GITHUB_SHA}`;
   - environment tag `development` hoặc `production` để tiện tham chiếu.
6. `develop` deploy lên EC2 bằng Docker Compose; EC2 pull image theo commit SHA
   từ Docker Hub và không build source trên máy chủ.
7. `main` deploy lên ECS Fargate bằng task definition mới trỏ tới image theo
   commit SHA.
8. **Vercel** là nền tảng deploy frontend React/Vite. Frontend được build và
   phát hành độc lập với backend, dùng URL API theo từng environment.
9. GitHub Actions là control plane của CI/CD: CI lint/test/build/push image;
   CD chỉ deploy sau khi CI thành công trên `develop` hoặc `main`.

## Luồng triển khai

```text
Push/merge develop or main
        |
        v
GitHub Actions CI
  lint -> test -> docker build -> push Docker Hub:${GITHUB_SHA}
        |
        +--> Vercel build/deploy frontend
        |
        +--> develop: GitHub Actions CD -> EC2 Docker Compose
        |
        +--> main: GitHub Actions CD -> ECS Fargate
```

### Môi trường

- `develop` deploy vào EC2 development với `docker-compose.dev.yml`.
- `main` deploy vào ECS Fargate production với task definition của ECS.
- Development có `.env` riêng trên EC2; file này không được commit.
- Production ECS nhận runtime configuration và secrets từ task definition,
  secret manager hoặc cơ chế secret của AWS; không dùng `.env` được tạo trên EC2.
- Docker Hub credentials, EC2 host, SSH key, JWT secret, database password và
  API keys được lưu trong GitHub Actions Secrets/Variables hoặc secret store
  của môi trường tương ứng.

## Lý do

Lựa chọn này tận dụng trực tiếp các thành phần đã có trong repository:

- `Dockerfile` tạo image backend reproducible.
- `docker-compose.yml` và các override dev/prod mô tả runtime backend và
  PostgreSQL/pgvector.
- `ci_cd.yml` build, test và push image lên Docker Hub theo commit; sau đó
  deploy `develop` lên EC2 hoặc `main` lên ECS Fargate.
- Vercel tách frontend khỏi lifecycle backend và phù hợp với React/Vite.

EC2 vẫn là môi trường development đơn giản cho MVP. Khi cần đồng nhất môi
trường hoặc giảm công việc quản lý EC2, development có thể được chuyển sang ECS
trong một ADR hoặc bản cập nhật ADR sau.

## Hệ quả

### Tích cực

- Backend không bị phụ thuộc vào source/build tool trên EC2.
- Commit SHA tạo ra release có thể truy vết và rollback.
- Frontend deploy nhanh, có preview và scale độc lập.
- Compose giúp giữ cấu hình local, development và production gần nhau.

### Tiêu cực và rủi ro

- EC2 development là điểm vận hành cần quản lý patch, firewall, disk, Docker và
  backup.
- PostgreSQL/pgvector hiện chạy cùng Compose trên EC2 development; production ECS
  cần cấu hình database/network riêng và chưa được mô tả đầy đủ trong ADR này.
- Docker Hub outage hoặc rate limit có thể làm chậm release.
- Self-hosted runner/SSH credentials là thành phần nhạy cảm cần hardening.
- Vercel và AWS tạo thêm hai hệ thống cần quản lý domain, CORS và environment
  variables.

## Biện pháp giảm thiểu

- Chỉ mở port cần thiết trên EC2; backend bind `127.0.0.1:8000` và đặt reverse
  proxy/load balancer khi public traffic yêu cầu.
- Dùng SSH key riêng cho deploy, quyền tối thiểu và rotate định kỳ.
- Dùng tag SHA làm tag release chính; không dùng `latest` cho production.
- Theo dõi disk/image cleanup và giữ tối thiểu năm release gần nhất.
- Kiểm tra `/health` sau deploy; rollback image trước nếu health check thất bại.
- Thiết lập PostgreSQL backup định kỳ và diễn tập restore trước production.
- Khi cần giảm phụ thuộc Docker Hub hoặc yêu cầu availability tăng, đánh giá ECR
  và RDS PostgreSQL trong ADR mới.
