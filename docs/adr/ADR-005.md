# ADR-005: TTL cache cho catalog API đọc nhiều

**Ngày:** 2026-10-05  
**Trạng thái:** Accepted

## Bối cảnh

Frontend thường xuyên gọi lại các danh mục công khai để tìm kiếm và chọn lịch
khám: chuyên khoa, cơ sở, dịch vụ và bác sĩ. Các dữ liệu này ít thay đổi hơn
so với availability và việc truy vấn lặp lại PostgreSQL làm tăng latency cũng
như tải database.

## Quyết định

- Dùng cache-aside in-process, bounded LRU và TTL mặc định 30 giây.
- Chỉ cache response của các public catalog endpoint sau khi đã xác thực.
- Lưu DTO đã serialize, không lưu SQLAlchemy ORM object gắn với session.
- Cache key bao gồm resource, filter, phân trang và ID detail.
- Xóa toàn bộ catalog cache sau mutation của staff để giảm stale data.
- Trả `X-Cache: HIT|MISS` và `Cache-Control: private, max-age=<TTL>` để frontend
  và vận hành quan sát được hành vi cache.
- Không cache availability/schedule vì remaining capacity thay đổi theo booking.

Cấu hình runtime:

- `CATALOG_CACHE_ENABLED` bật/tắt cache.
- `CATALOG_CACHE_TTL_SECONDS` điều chỉnh TTL.
- `CATALOG_CACHE_MAX_ENTRIES` giới hạn số key trong mỗi process.

## Đánh đổi và rollout

Cache in-process không đồng bộ giữa nhiều worker hoặc nhiều instance. TTL ngắn
giới hạn thời gian stale; khi scale ngang cần thay backend bằng Redis dùng chung
và invalidation qua pub/sub. Hiện tại lựa chọn này không thêm dependency hay
service vận hành mới, phù hợp với deployment hiện có.

Rollout bằng cấu hình mặc định, theo dõi `X-Cache` và latency/database load.
Nếu cần rollback, đặt `CATALOG_CACHE_ENABLED=false` mà không thay đổi API contract.
